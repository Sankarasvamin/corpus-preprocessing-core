# 0001：先固定跨语言数据契约

- 状态：已接受
- 日期：2026-08-20
- 范围：阶段 1 可复现基础

## 背景

新闻类文章、评论和回复来自 JSONL、TSV、HTML 等不同格式。后续还要连接抽样、确定性清洗、模糊模板清洗、去重、canonical 选择、质量评分和交付审计。若各阶段或两种语言各自解释字段，结果即使都能运行，也无法复核。

## 已确认的设计

1. 先以 JSON Schema 固定 `RecordV1`、`CleaningEventV1`、`SamplePlanV1` 的边界。
2. `RecordV1` 顶层字段全部必填；`event_date`、`title`、`clean_text` 必填但可空。扩展信息进入 `metadata`，不放任顶层字段漂移。
3. Python 是可读、便于迭代的参考实现；Rust 是后续性能路径。两者必须读取同一真值 fixtures，并比较完整 profile JSON，而非只比较几个计数。
4. 合成数据生成器接受固定 seed，生成原始坏数据、合法标准化真值和机器可读注入清单。这样既能回归异常边界，又不暴露公司或私人数据。
5. profile 只做统计，不清洗文本、不推断近似重复，也不改变输入。

## 当前合理假设

- `record_type` 阶段 1 只接受 `article`、`comment`、`reply`；总清单早期草案中的 `other` 暂不进入本契约。
- 日期使用 `YYYY-MM-DD` 形状或 `null`；阶段 1 不替业务决定时区、事件时间与抓取时间的优先级。
- “缺失标题”定义为 `null` 或去除首尾空白后为空；“缺失或空正文”基于 `raw_text` 同样判断。
- “重复 record ID 数”定义为重复出现次数，即总数减唯一 ID 数，而不是重复组数量。
- `source_offset` 采用非负 `u64` 范围，以保证 Python/Rust 可表示范围一致。

## 为什么暂不实现下游算法

模糊清洗、精确/模糊去重、strict STAR clustering、canonical 选择与质量评分都依赖尚未校准的阈值、特征、权重或业务标签。阶段 1 若提前加入，只会把匿名化示例参数误写成实习事实，也会让契约变更同时破坏更多代码。本阶段用带真值标记的反例保留测试入口，下一阶段再逐项实现。

## 后续需要校准的实习细节

- 原始格式到 `RecordV1` 的实际字段映射与 `source_offset` 口径。
- 日期字段的业务优先级、时区和非法日期处理策略。
- 清洗事件中 `stage`、`action`、`reason_code` 的正式枚举。
- 抽样分层键、最小层样本量和 allocation 方法的真实参数。
- 模糊清洗与去重的候选生成、阈值及人工复核灰区。
- canonical 的原始优先级、质量评分维度权重和三分类业务名称。
- Leave-One-Category-Out 的下游任务、指标、等量删除对照和训练预算。
